# World-of-Osso periodic audit checklist

## Contract and timing

This is an agent-readable, report-only audit for a live Pi main World-of-Osso session. This project-owned checklist is `periodic-checks.md` at the game-engine Git root; the generic filename lets other Git projects opt in with their own policy. Reread this checklist for each audit. At `session_start`, the session-local extension arms a 30-minute timer only if this checklist exists. If removed after startup, the next tick stops the timer without an audit. Restoring the file does not automatically rearm it: the next `session_start` must find it present, then wait a full 30 minutes before the first tick. Subsequent ticks occur every 30 minutes; restart resets the wait. No persistent scheduling or catch-up work is authorized.

Current dispatch requires an idle main with no pending messages and no live audit child. Busy ticks are skipped, not queued for immediate delivery when main becomes idle. An idle eligible tick triggers main to delegate; a missing first audit is not proof of a successful audit. Unavailable multi-agent tools/store, unsupported session mode or project scope can prevent dispatch. Report timing gaps only with evidence; do not repair scheduling.

Audit child must not edit files, deploy, delete or clean anything, cancel work, block main, steer ongoing work, spawn agents (including nested delegation), or create, start, stop, reset, rearm or otherwise operate timers/services/loops. Continue main's authorized work independently. Findings are recommendations for main, not permission to act.

## Scope and evidence

Derive the audited host's World-of-Osso project-family root from the parent directory of the canonical game-engine Git checkout, not `~/Projects` or any fixed host path. Resolve the checklist's Git root through read-only Git metadata. For a canonical checkout, use its parent World-of-Osso directory. For a linked worktree outside that family, use the Git common directory and canonical checkout/worktree metadata to establish the canonical game-engine checkout and then its parent. Do not treat the external worktree's parent as the family root. If metadata is missing, inaccessible or ambiguous, report family scope and inventory coverage unknown rather than guessing a root or substituting another discovery source. Inspect its immediate child directories within explicit traversal, output and duration bounds; identify actual Git repositories from repository metadata, not directory names. Report a missing or inaccessible root, inaccessible or unclassified child directories, or a bound that prevents complete discovery as unknown inventory coverage. Do not invent coverage for unobserved paths.

Inspect all discovered participating repositories together, not just main's cwd or the remote launch selectors. Use read-only Git worktree metadata to discover and include their associated worktrees, even outside the root; report inaccessible or unclassified worktree paths as unknown coverage. Confirm existence and participation from read-only repository/session evidence. Do not restrict discovery to launch selectors or a stale KB list; no KB inventory is required at runtime.

Bound command output, filesystem traversal and observation duration. Use existing status, timing and resource evidence; do not start builds, tests, benchmarks, cache warming, or expensive full-tree scans. Stop a probe at its bound and report the evidence gap; do not wait for other agents or interrupt their work. Use supported session/history tools, not raw transcript-store searches. Never read secrets or forward sensitive logs, credentials, environment dumps, private prompts or raw terminal scrollback. Summarize redacted errors only.

## Read-only checks

1. **Cleanup candidates and storage.** Read repository/worktree status, merge or patch-equivalence evidence and live ownership. Identify only candidates positively shown to be clean, merged/patch-equivalent and unowned. Preserve canonical/default, dirty, active-owned and unique-work branches/worktrees. Missing PRs or suggestive branch names do not prove merge status. Never delete anything. Measure filesystem free space and bounded build-artifact sizes; compare growth only against a timestamped prior observation of the same paths. Without a baseline, report size and growth unknown. Do not label artifacts safe to remove without evidence that no live build/work owns them and they contain no unique needed output.
2. **Build speed, cache contention and errors.** Compare existing build timings only for comparable commands, revisions/workloads, profiles/features, host/resources and cache state. State material differences; otherwise comparison is unknown. Inspect available cache/lock wait and concurrent-build evidence across repositories. Distinguish observed contention from hypotheses. Summarize current build failures with repository, sanitized error, time/revision and unresolved/resolved evidence; do not rerun builds to establish a comparison.
3. **Main errors and delegation lifecycle.** Inspect available supported main-session evidence for unresolved errors and subsequent recovery proof. Count delegation lifecycle states (running, pending, completed, failed, aborted or the actual exposed labels), with timestamp, session scope and source. Do not equate terminal status with accepted/verified output. Distinguish stale/unknown ownership and missing state from confirmed failure; do not cancel or restart agents.
4. **Host headroom and independent work.** Observe CPU load/available capacity, available memory and pressure, filesystem free space and disk I/O pressure. Include applicable cgroup/slice limits and active builds/agents when observable, not merely host totals. Recommend main consider more subagents only when identifiable authorized independent work exists and measured CPU/memory/disk headroom supports it without worsening contention. State task independence and supporting measurements. If either evidence is unknown or headroom constrained, do not request more agents. Never spawn them yourself.

## Reporting

Send findings with `send_agent_message` using both recipient fields supplied by parent dispatch: `toAgentId: "main"` and `toSessionId: <provided parentSessionId>` (the originating parent Pi session ID). Write the report text alongside the tool call and check that the send succeeded. A failed send is not a delivered finding; no fallback routing is authorized. Main must explicitly confirm mailbox receipt from its own supported mailbox evidence; successful send alone is not receipt proof. Do not use wait recovery as delivery or receipt evidence, and do not wait for main acknowledgement or recovery in the audit child. Send only changed actionable findings relative to the previous audit report available through supported session/message evidence. Include newly observed actionable evidence gaps or changed unresolved risks, not repetitive all-clear/status messages. If prior-report evidence is unavailable, label the comparison unknown and send only current actionable findings; do not invent a baseline or persist one in files.

Each finding states repository/host/session scope, observation time, sanitized evidence, change from known baseline, consequence and a report-only recommendation. Explicitly mark unknown measurements, comparability, resolution, ownership and inventory coverage. Keep facts separate from hypotheses. No finding means no findings message; a missing report does not establish that every check passed. Main reports findings only; audit grants no cleanup, cancellation, blocking, automatic spawning or other operational authority.
