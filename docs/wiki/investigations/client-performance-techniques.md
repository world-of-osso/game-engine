# Client performance techniques for Stormwind

Read-only source comparison, 2026-10-30. No builds, measurements, or code changes. Goal: 120 FPS at 1080p in a Windows release, indoors and at the Stockade exit. User-supplied indoor baseline: render thread 7.6 ms, main 7.2 ms, 4,650 draws including 1,080 shadow draws; exit 166–179 FPS. The earlier Linux investigation is [godot-stormwind-fps](godot-stormwind-fps.md); [solarity comparison](solarityclient-performance-comparison.md) describes the **retired Bevy client**, not the current Godot code. The solarity checkout has since changed; citations below are to its current source.

**Estimates below are hypotheses, not benchmark results.** Draw savings cannot be added: techniques remove overlapping work, and shadows, occlusion, transparency, and Godot's automatic batching change the result. A draw removed is not a fixed number of milliseconds. Verify with a pinned Windows release, same 1080p camera path and scene, warmed assets, frame-time distributions, render/main/GPU timings, pass-specific draws, and image comparisons both indoors and across the exit. Keep shadows and off-screen casters correct.

## Ranked candidates

1. **Restrict outdoor admission to the visible exterior portal window.** Solarity derives an outdoor screen window from the camera WMO root, creates a clipped frustum from it, and only queues ordinary outdoor groups when that window exists (`/home/osso/Repos/solarityclient/crates/runtime/src/application/terrain_coordinator/movement/scene/admission.rs:100-128`). It also separately considers moving overlap roots (`:165-180`): “inside” is not a safe blanket hide. Our WMO traversal explicitly draws the *whole* exterior once one portal opens (`godot/rust/src/wmo/portals.rs:1-5`); `cull_wmos` applies it to WMO groups (`godot/rust/src/terrain/objects.rs:1151-1176`), while ADT doodads are processed separately (`:1180-1193`). Extend visibility admission across outdoor terrain, ADT props and other WMOs using conservative portal windows, including multiple portals and transition/overlap cases; do not assume an entire exterior can be hidden merely because the camera is indoors. **Estimate:** potentially hundreds to thousands fewer indoor submissions; 0–2+ ms render-thread improvement is plausible but unmeasured, and benefit can be zero when the portal is wide or existing frustum/occlusion already removes them. **Cost/risk:** high; shared cross-system visibility, outdoor objects spanning cells, doorway popping, portal near-plane and sky/shadow correctness. Agent_19131 is implementing interior outdoor-ADT hiding and occlusion; clipping outdoor admission through visible portal windows and accounting for multiple WMOs is a possible refinement beyond that stated scope.

2. **Consolidate compatible surfaces, not merely nodes.** WebWowViewerCpp has a Vulkan GPU indirect/bindless path (`/home/osso/Repos/WebWowViewerCpp/wowViewerLib/src/renderer/mapScene/vulkan/indirect/GpuIndirectDrawsVLK.cpp:19-21`, `BindlessIndirectDrawsVLK.cpp:1-9`); it is not a stock Godot rendering path. Godot Forward+ submits per render-list surface (`/home/osso/Repos/godot-4.7.2-src/servers/rendering/renderer_rd/forward_clustered/render_forward_clustered.cpp:305-351,598-617`). Merge only compatible WMO or terrain geometry *into the same surface/material*, with texture arrays/atlases or material sharing where justified; a multi-surface mesh does not itself remove surface draws. Our terrain builds one mesh and material per chunk (`godot/rust/src/terrain/material.rs:216-240,265-266`); current WMO batches remain separately visible (`godot/rust/src/terrain/objects.rs:1161-1174`). **Estimate:** 0–hundreds of draws and 0–1+ ms, entirely dependent on compatible materials and the portion actually visible; measure material identity before committing to an atlas. **Cost/risk:** medium–high; geometry, UVs, material/lighting differences, transparency ordering, shadows and culling granularity. Agent_19131's stated scope does not include merging distinct compatible WMO or terrain surfaces; this is a separate candidate.

3. **Make repeated static M2 surfaces genuinely batchable, then measure automatic instancing before adding MultiMesh.** Godot Forward+ already combines consecutive matching render-list entries: same sort keys and mirror state, but not MultiMesh or instances with a mesh instance (`render_forward_clustered.cpp:877-905`); one call can then draw the repeats (`:598-617`). Reusing a mesh is therefore necessary but not proof of batching: material identity, animation/skinning, pass and state matter. Explicit MultiMesh is a separate choice with group-level visibility; partition it spatially to avoid trading fewer draws for excessive overdraw. WebWowViewerCpp's Vulkan path has per-model shared animation data (`/home/osso/Repos/WebWowViewerCpp/wowViewerLib/src/renderer/mapScene/vulkan/GpuM2AnimationVLK.cpp:232,500`), but that is not evidence that Godot can automatically batch separately skinned placements. Our doodad path drives individual animation (`godot/rust/src/terrain/objects.rs:1180-1193`); the measured node/batch costs are in [the investigation](godot-stormwind-fps.md#wmo-doodads-branch-wmodoodadcost). **Estimate:** zero to hundreds of draws, depending on actual repeated visible mesh/material pairs; automatic instancing may already realize some savings. **Cost/risk:** medium for rigid sharing; high for animated M2, per-instance fade/light, transparent ordering and coarse MultiMesh bounds. Agent_19131 is moving static doodads to RenderingServer or MultiMesh; measuring Godot automatic batching and material identity first is a refinement of that work, not an independent lane.

4. **Use spatial references as a candidate index, not a full doodad walk.** WebWowViewerCpp visits ADT quadtree ranges and invokes chunk reference collection (`/home/osso/Repos/WebWowViewerCpp/wowViewerLib/src/engine/objects/adt/adtObject.cpp:1110-1141`); modern MCRD references select candidate M2s, and MCRW selects WMOs (`:1347-1374`). Its older MCRF block is commented out (`:1325-1344`), so do not claim that block executes. wowser-scene first tests area spheres then individual doodads (`/home/osso/Repos/wowser-scene/src/lib/map/DoodadManager.ts:38-65`), although it still loops its area's children to hide them. Our `cull_doodads` visits every doodad (`godot/rust/src/terrain/objects.rs:1180-1193`). Maintain deduplicated cell/group candidate membership and changed visibility state, preserve objects crossing cell boundaries, and process animation/fade for admitted candidates. **Estimate:** 0 draws saved by itself if it preserves the same visible set; potentially 0–several ms main-thread time, not directly render-thread time. Prior debug cull timings are not Windows release estimates. **Cost/risk:** medium–high; membership bookkeeping, portals, dynamic objects, culling transitions. Agent_19131 is implementing grid/cell visibility for static doodads; ADT-authored references and candidate deduplication are a possible alternative or refinement, not a separate immediate lane.

5. **Separate camera visibility from shadow-caster admission.** Solarity independently collects exterior WMO shadow groups and their MODR doodads per shadow map, not just portal-visible geometry (`/home/osso/Repos/solarityclient/crates/runtime/src/application/terrain_frame/world_model/shadow.rs:1,13-55,74-83`). Our WMO doodad path already disables shadows based on shadow-group membership (`godot/rust/src/terrain/objects.rs:1119-1120,1292-1297`). Audit which remaining 1,080 draws belong to cascades, terrain, WMO and doodads; then use conservative light-frustum/cascade membership or authored non-caster flags where supported. Do not hide a caster solely because it is outside the camera frustum; it may cast into the visible room. **Estimate:** 0–hundreds fewer shadow draws and 0–1+ ms render-thread time, conditional on actual unnecessary casters and cascade duplication. **Cost/risk:** medium–high; moving sun/camera invalidates static assumptions, missing shadows and mismatched indoor/outdoor lighting. Agent_19131 is implementing shadow-pass LOD and small-caster culling; source-driven WMO/MODR and per-cascade admission is a distinct refinement, subject to overlap in the final implementation.

## Additional boundaries

- **Occlusion:** WebWowViewerCpp has a Hi-Z occlusion stage with a barrier to indirect culling (`/home/osso/Repos/WebWowViewerCpp/wowViewerLib/src/renderer/mapScene/vulkan/view/HiZOcclusionCullingVLK.cpp:338`). Godot's stock OccluderInstance3D/raster occlusion is a different implementation, not that GPU-driven pipeline. User identifies missing occluders and agent_19131 is addressing them. Test conservative wall geometry, doors and moving camera; occluder CPU cost and shadows must be included. Source checkout is a partial Godot tree and lacks its occlusion implementation, so its detailed behavior was not verified here.
- **Terrain merging:** Solarity's retained investigation reports one merged geometry buffer and blend/shadow atlas per tile ([comparison](solarityclient-performance-comparison.md#where-the-frame-cost-goes-away)). Larger Godot regions sacrifice frustum/occlusion granularity and can draw more hidden terrain indoors; use spatial clusters, not necessarily whole tiles. Included in item 2.
- **M2 LOD/skin profiles and impostors:** potentially reduce distant geometry or surfaces; neither the actual available alternate profiles nor their current runtime selection was established. Lower priority with GPU at ~40%; triangle reductions alone do not prove CPU draw savings. Do not assume an authored LOD has fewer materials. Godot visibility-range/HLOD would require separate assets and careful transitions; its implementation is absent from the partial source checkout.
- **Nodes versus RenderingServer:** fewer SceneTree nodes can reduce creation, memory and per-node work, but does not automatically remove renderer instances or surface draws. Godot's automatic batching excludes mesh instances in the cited code, making rigid versus skinned classification important. The existing investigation says node count itself had no identified per-frame cost in its samples; do not infer a Windows ms gain without profiling.
- **Directional shadow caching and threading:** the available Godot source subset does not establish reusable directional-shadow caching behavior. Do not assume static shadows are cached across sun or camera changes. The project already sets `driver/threads/thread_model=2` (`godot/project.godot:31`); changing that setting alone is not evidence of less total work, and sync/stall behavior needs a Windows profiler A/B. Do not change it based on the setting name.
