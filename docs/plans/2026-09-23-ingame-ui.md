# Complete in-game UI: coverage matrix and screen layout

**Status:** Design proposal. No implementation is authorized by this document. Supersedes the
combat-only scope boundary in [combat HUD initial design](2026-09-23-combat-hud.md); its accepted
combat decisions stay in force.

## Accepted decisions (user)

- Modern combat HUD. Game windows keep a familiar WoW style.
- Combat uses a central cluster above the bottom-center action bars.
- Combat frames: thin metal borders, dark backing, no portraits, familiar spell artwork.
- Combat is the first implementation slice, not the project limit.
- Keep registry-backed Bevy UI and `rsx!`/`Screen`. Character creation is accepted as is.
- Each phase includes its `shared-protocol` and `game-server` work. No window ships implying gameplay the server does not perform.
- Delivery by vertical slice: each phase fixes its protocol messages as the contract, builds server and client against it, and ends with a live-server test (`dump-ui-tree` + screenshot).
- Game windows use authored Retail FDID art from local CASC.
- Windows open in WoW-style auto slots and are movable, with saved positions.
- UI auto-fits: effective scale = `min(w/1920, h/1080) × user_scale`, minimum supported viewport 1280×720.
- Party/raid frames sit near the central cluster (left of the player frame, above chat).
- Square minimap with a thin metal border.
- Retail-style tabbed chat. The combat log is a chat tab with resolved names.
- HUD edit mode can move every HUD element, as in WoW Edit Mode.
- Full DB2-driven spell system (effects, auras, procs, resources, cooldowns, spellbook, talents) for every character-creation class, all at once.
- Quest, vendor, trainer, loot and gossip content comes from an extended AzerothCore import into world SQLite. Mapping is Retail-first: keep rows whose id+name match Retail; item attributes from Retail DB2; class spells from Retail skill lines (AzerothCore trainer ranks dropped); quests only if the id exists in Retail QuestV2; Retail taxi tables; a small reviewed rename table. Unmatched rows are dropped and listed in a report.

The rest of this document is proposal unless it restates one of these decisions.

## Status codes

| Code | Meaning |
|---|---|
| **LIVE** | Visible in game and backed by live server data or actions |
| **LIVE-RO** | Visible, shows live data, but player actions are missing |
| **SHELL** | Mounted in game, but its data is empty, local, or hardcoded |
| **UNMOUNTED** | An `rsx!` component exists but is used only by tests, or its plugin is never added |
| **IPC** | The backend works, but can only be driven through the dev CLI/IPC socket. No UI |
| **MODEL** | A client data type exists, with no UI and no backend |
| **ABSENT** | No code |

"Server" column: **yes** = the server handles it; **partial** = described in the cell; **no** = no
handler or message.

## Proposed screen composition

The layout uses a 1920×1080 reference canvas in UI units. Every element is anchored to a screen
edge or to the center, not to absolute pixels.

**Regions**

- **Bottom-center (combat, accepted):** the central cluster of player, resource/cast and target
  frames is about 760 wide. It sits above two 12-slot rows. Target-of-target and focus sit to the
  target's right.
- **Bottom-left:** chat.
- **Bottom-right:** micro menu, bags bar, and optional vertical side bars (bars 3–5).
- **Top-right:** minimap, with player auras to its left and the objective tracker below it.
- **Top-center:** transient text: zone entry, errors, raid warnings. Popups sit under it.
- **Left edge, 30–60% height:** party/raid frames.

**Width budget:** chat 430 + cluster 760 + bags/micro 330 + gutters is about 1600 of the 1920
reference width. So 16:9 and wider screens fit without overlap. Narrower aspect ratios keep the
full reference width and gain height.

**Window classes (proposal, like WoW's UIPanelLayout)**

| Class | Members | Placement | Coexistence |
|---|---|---|---|
| Panel | character, spellbook, quest log, social/friends, guild, reputation, professions, merchant, mail, trainer, gossip, quest dialog, trade, inspect, bank, loot rules, calendar | Slot L (x=16, y=104). A second panel goes to slot R, next to the first | At most 2. Opening a third closes the oldest. NPC-driven panels (merchant, mail, bank, gossip) take slot L and push the others right |
| Wide | world map, auction house, talents, collections, achievements, encounter journal, LFG, PvP, barber, transmog | Centered, max 1000×680, top at y=104 (clears the cluster at 1080) | Exclusive with all panels except bags |
| Container | bags | Anchored bottom-right, stacking | Free; coexists with everything |
| Popup | confirmations, rez, ready check, invites, duel, quantity entry | Top-center stack, DIALOG strata | Up to 3 stacked. Modal only for their own input, not for world input unless destructive |

**Overlap:** panels may cover the party frames and part of chat, as in WoW. Nothing may cover the
combat cluster except wide windows, which stop at y=784.

**Scaling:** effective scale = `min(w/1920, h/1080) × user_scale`. The minimum supported viewport and
minimum readable font size are open decisions. At 1280×720 the effective scale is 0.667, which turns
12-unit text into 8 px.

## Shared interaction rules (proposal)

1. **Input focus modes.** Exactly one is active at a time:
   - **World:** keybinds are live.
   - **Text:** an editbox has focus. Every keybind except Enter and Escape is suppressed.
   - **Modal:** a popup or fullscreen window is active. Only its keys work.
   - **Drag:** something is on the cursor.

   One resource owns the mode, and every keybind system checks it. This replaces the per-screen
   checks.
2. **Escape, in order, one action per press:**
   1. Clear editbox focus.
   2. Drop the cursor item or cancel spell targeting.
   3. Close the top popup.
   4. Close all panels and wide windows.
   5. Clear the target.
   6. Open the game menu.

   This fixes the current double action.
3. **Enter** focuses the chat input. `/` and `R` open the input prefilled.
4. **Tooltips:** one shared tooltip builder for spells, items, units and auras. It shows after
   about 150 ms and attaches to the hovered frame, clamped to the screen. Shift-compare for items.
5. **Links:** clickable `[Item]`/`[Spell]` tokens in chat. Shift-click on an icon inserts a link
   when the chat input has focus.
6. **Drag-and-drop:** a single cursor item holds a spell, item, macro or money. Left-drag picks up
   and left-click drops. Right-click on an item uses it. Shift-drag splits a stack through a quantity
   popup. Escape cancels. Only drop targets that the server supports accept a drop.
7. **Context menus:** right-click on a unit frame, nameplate or chat name opens one shared menu.
   Entries are shown only when their backend exists.
8. **Scrolling:** a shared scroll list with virtualized rows, wheel, drag thumb, and
   keyboard PgUp/PgDn. Used by the quest log, AH, mail, friends, guild and chat.
9. **Search and filter:** one shared search box. Debounced typing searches locally. Server searches
   run on Enter or after 300 ms idle.
10. **Quantity input:** a shared stepper and editbox with max, min and "all", showing the total cost
    live.
11. **Confirmations:** required for destructive or expensive actions: destroy, buyout above a
    threshold, sending mail with money, learning or resetting talents, abandoning a quest, leaving a
    group. A confirmation shows exactly what changes, and Enter confirms only when focused.
12. **States:** every data-backed surface renders explicit states:
    - *loading*: request in flight, with a spinner and a timeout
    - *empty*: the query returned nothing
    - *error*: server rejection text
    - *unavailable*: no backend yet
13. **Unsupported features** show as disabled with "Not available yet". A button never looks usable
    when it does nothing (today the LFD, Collections and minimap Mail/Zoom buttons do exactly that).
14. **Keyboard navigation:** Tab and Shift+Tab move between editboxes within one window. Arrow keys
    move through list selection. Panel toggles become bindable actions instead of hardcoded
    `KeyCode`s.
15. **Window behaviour:** clicking a window raises it (writes `raise_order`). Moving windows and
    saving their positions is an open decision.
16. **Testing:** in-world JS automation needs click and key support (today only login and
    character screens have it). Every phase's acceptance runs through `dump-ui-tree` and a
    screenshot on a live server.
