**Menu evidence, as supplied:** `UnitPopup.lua` reads `ITEM_QUALITY_COLORS[2..4]` while defining the quality menu buttons, so those color entries must exist before that Lua executes; the excerpt does not identify their defining file. `RAF_SUMMON` and `RAF_GRANT_LEVEL` are listed for PARTY, PLAYER and RAID_PLAYER menus. These Lua wiring and menu predicates are cache evidence, not independently verified shipped-12340 UI.

**Native API evidence:** `SummonFriend(unit)` and `GrantLevel(unit)` are registered globals; each consumes the first Lua string through the unit/name-to-GUID resolver and returns zero Lua values. The resolver accepts unit tokens and names resolvable to current player/party/raid/arena units; this is not a Battle.net presence-ID API. `SummonFriend` checks RAF eligibility, may report a UI error/name-cache result, then casts the summon-friend spell (temporarily targeting the selected GUID if necessary). `GrantLevel` checks player/RAF eligibility and sends `CMSG_GRANT_LEVEL` for the target when allowed; denied calls display a UI error.

- `IsReferAFriendLinked(unit)`: one string argument; returns numeric `1` or nil according to the active player's RAF check.
- `CanSummonFriend(unit)` and `CanGrantLevel(unit)`: one unit/name string; return numeric `1` or nil as UI predicates. Their underlying player checks decide action eligibility.
- `GetSummonFriendCooldown()`: no argument; returns three numbers (start, duration in seconds, enabled flag).
- `ReportPlayerIsPVPAFK(unit)`: one string unit token; returns no values. It acts only when the active player exists, target is not self, and target is in party or raid.
- `GetLootThreshold()`: no argument; returns one number.
- `SetLootThreshold(threshold)`: one numeric threshold; valid values 2–6; returns no values. It requires a party/raid and active-player leadership, otherwise displays an error and returns. Successful calls update the loot method.

These native handlers support the existence and their own argument/return behavior, but cannot prove that the supplied `UnitPopup.lua`/`FriendsFrame.lua` content was shipped with the client.

The native 12340-facing report global found is **`BNReportPlayer`**, not `BNet_InitiateReport`:

- The wrapper is registered in `BattlenetUI_Scripts.cpp:1690`; the handler is `:1017–1057`.
- When the Battle.net/login/RID prerequisites are not satisfied, it does nothing and returns zero values. Otherwise it requires argument 1 numeric presence ID and argument 2 string report type; wrong types raise Lua errors. Type names are case-insensitive `SPAM`, `ABUSE`, `THREAT`, and `NAME`; other strings raise “Unknown Reason.” Optional argument 3 is used only when it is a string; a note over 127 UTF-8 characters errors. It returns zero Lua values.
- The wrapper calls `BattlenetAPI::ReportPlayer(presenceID, reason, note)`, which delegates to the external `BattlenetAPI_ReportPlayer` function through the Tumor manager (`BattlenetAPI.cpp:225–232`). This is the client-side report-service handoff; the reconstructed path does not expose the remote transport/result protocol.
- There is no `REPORT_PLAYER_RESULT` or other report-result event in the inspected source. If the immediate external call returns zero, the wrapper adds the localized `BNET_REPORT_SENT` text to the local chat frame. That is a local chat message, not an event or a demonstrated remote-success callback. No further network completion timing/order is established.

`BNet_InitiateReport(presenceID, reportType)` is UI Lua in the requester-supplied 30300 cache, not a native C++ binding found in W. The cache lists SPAM/ABUSE/NAME in the submenu (THREAT is defined but omitted), although native `BNReportPlayer` also accepts THREAT.

## Q4 — quest loading and results

No `C_QuestLog.RequestLoadQuestByID`, `QUEST_DATA_LOAD_RESULT`, or `QuestEventListener:AddCallback` registration was found in pinned W. Thus the native reconstruction provides no such Lua event payload/order.

The native quest-cache path is different:

1. `g_questDBCache` is backed by `questcache.wdb` and uses `CMSG_QUERY_QUEST_INFO` (`DBCacheInstances.cpp:49`). A loaded cache entry is returned directly by `GetRecord`; this path does not call a pending callback or emit a script event (`DBCache.h:295–341`).
2. On a cache miss, `GetRecord` with a callback stores the callback, submits a single-key query using `ClientServices::Send2`, and returns null (`DBCache.h:302–319,375–388`). Submission alone establishes no response timing.
3. `ReceiveQuest` unpacks the reply. A nonempty quest name is added/marked loaded and pending callbacks are invoked with `(questID, guid, param, true)`; an empty name denies the cache entry and callbacks receive `(questID, guid, param, false)` (`DBCacheInstances.cpp:134–144`; `DBCache.h:573–620`). This is a C++ cache callback, not `QUEST_DATA_LOAD_RESULT`.
4. The native `GetQuestLogQuestText` caller returns two nils when the record is still missing and returns description/objectives when cached (`QuestLog_Scripts.cpp:467–487`). For this caller, a successful cache-miss response invokes `QuestQueryCallback`, which queues a deduplicated `QUEST_LOG_UPDATE` unique signal without payload (`QuestLog.cpp:257–263`; `ScriptEvents.cpp:209–221,321–337`). The queue is drained from `CGGameUI` update after `DBCache_Idle` (`GameUI.cpp:2072`); source does not establish an exact delivery time relative to request submission. A denied/unknown response only logs `Invalid quest log entry` and queues no signal. This is not the modern `QUEST_DATA_LOAD_RESULT` event.

Therefore a cached lookup returns data immediately to its caller without a cache callback or load-result event. A miss initiates a query; a successful response then invokes the cache callback and queues the legacy `QUEST_LOG_UPDATE` for the signal-drain boundary, while an empty/denied quest response invokes the failure callback and queues no event. Request submission alone establishes no response timing. No modern request/event payload or order can be claimed because those names were not found.
