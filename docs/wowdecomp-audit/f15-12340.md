## Q2 — AutoHide and attribute-change path

**Generic native attribute behavior, not AutoHide behavior:** `SetAttribute(name, value)` requires `ProtectedFunctionsAllowed()` or `AttributeChangesAllowed()`; otherwise it invokes blocked-action feedback and returns. `AttributeChangesAllowed()` accepts when the frame or an ancestor carries the corresponding flag. Once permitted, the wrapper stores the attribute and calls `CSimpleFrame::SetAttribute`, which invokes the `OnAttributeChanged` script path synchronously. That path passes the lowercased name and value, and temporarily clears/restores `lua_tainted` unless executing a tainted closure. This says nothing about the absent AutoHide implementation or secure handle semantics.

## Q3 — secure click handlers and native action paths

W does not contain the `SecureUnitButton_OnClick` / `SecureActionButton_OnClick` implementations or SecureTemplates Lua/XML. Consequently it cannot establish, for target/focus/assist/macro/spell/action types, the handlers’ accepted mouse phase, `down` value, hardware-event requirement, secure execution context, OOC direct-call validity, complete event order or whether `down=false` then `down=true` is a valid retry.

The native physical button path is narrower and explicit:

- Mouse-down reaches `CSimpleButton::OnLayerMouseDown` and invokes `OnClick(button, 1)` on a matching click mask.
- Mouse-up on a pushed button satisfying release-mask and pointer-hit tests invokes `OnClick(button, 0)`, except a qualifying second click may invoke `OnDoubleClick` instead. When `OnClick` runs, its callbacks are `PreClick`, `OnClick`, then `PostClick` synchronously. `RegisterForClicks(...)` is implemented: it maps each string such as `LeftButtonDown` or `LeftButtonUp` to a distinct click-mask bit, ORs the bits and stores the mask. Lua `Click()` directly invokes `OnClick`; it does not synthesize the mouse-routing/hit-test path.
- Protected calls use `ProtectedFunctionsAllowed()`; native target/focus setters also test taint. A direct Lua call is not proof of a physical hardware event or secure-template authorization.

Core counterparts, not proof of secure-button dispatch:

- Target APIs resolve/validate a target and update local selection. On a valid target, native order is local target bookkeeping, `CMSG_SET_SELECTION` send, spell-usability update, then `PLAYER_TARGET_CHANGED`; target clear sends a zero selection and signals the event when using the event-producing clear path.
- `FocusUnit` resolves a unit token and calls `SetFocusTarget`; the setter rejects tainted calls, updates focus and then signals `PLAYER_FOCUS_CHANGED`.
- `AssistUnit` resolves a source unit, reads its target, targets that GUID when present, and may enter combat under `assistAttack`.
- Macro execution signals `EXECUTE_CHAT_LINE` for each nonempty, non-comment line. Action-bar `UseAction` dispatches by stored action type; spell APIs route into spell-cast paths. These lower-level mappings do not establish the missing secure click handler’s ordering or completion before Lua returns.

Native combo-point behavior:

- `SMSG_UPDATE_COMBO_POINTS` reads a target GUID and point byte and calls `CGGameUI::UpdateComboPoints`.
- `UpdateComboPoints` stores target/count, updates spell usability, then calls `Script_SendUnitSignal(activePlayer, UNIT_COMBO_POINTS)`. That helper directly signals matching unit-token events with the token payload; source order is stored state → spell usability → event dispatch. Repeating with count zero stores zero and signals the same event; no FrameXML display change follows from this C++ path alone.
- `GetComboPoints("unit"[, "target"])` resolves both unit tokens; it returns a number for the active player (class 4 or 11) or active pet. Player lookup returns stored points only for the stored combo target, using locked target when the target token resolves to zero; otherwise zero.

These do not prove `TargetFrameContainer.Portrait`, `CircleMask`, `ReplaceOtherPlayerPortraits`, or a restricted AuraButton public/forbidden Count partition. Those template names/partitions were not found in W; absence from this partial reconstruction is not proof of runtime absence.

## Q5 — tooltip fade and UnitFrame callback field

Native tooltip state does not include the FrameXML `frame.UpdateTooltip` property. W contains no `UpdateTooltip` reference and no native `Hide`, `FadeOut`, `SetOwner` or `OnTooltipCleared` path explicitly clears an arbitrary source frame’s Lua field. A Lua callback could do so, but that requires target UI code not present here.

- `GameTooltip:GetOwner()` returns the native owner frame or nil. `SetOwner` clears tooltip contents, restores alpha/stops fading, then updates the owner/anchor unless the requested owner/anchor/offsets already match, in which case it returns after the clear/reset.
- Native `SetUnit("unit"[, hideStatus])` calls the tooltip unit builder; a valid unit can build lines and show the tooltip even when the method returns zero. Its numeric return is nonzero when the threat row is added; the wrapper returns `1` in that case and nil otherwise. Thus `frame.UpdateTooltip` assignment in Lua depends on that return, not merely on `unit == "player"`.
- `FadeOut()` hides cursor/cursor-right anchored tooltips immediately. Other anchors start a 2.0-second fade; when elapsed reaches zero the native update restores alpha and calls `Hide()`. `HideThis()` clears native owner/content through `SetOwner(nil, ...)` before base-frame hide. A normal non-cursor tooltip therefore remains visible with its owner during the fade, then becomes hidden with owner nil. Exact anchor/initial visibility depend on the missing UnitFrame Lua path.
- The supplied 30300-cache note says its UnitFrame leave helper takes no `self` and calls only `Hide`/`FadeOut`, while the successful `SetUnit` branch sets `UpdateTooltip`. If that excerpt is exact, the leave helper itself leaves the field unchanged. The local cache containing the exact 30300 file is not available on this host, so that detail is reported cache evidence, not independently checked or shipped-client proof. The `SHOW_NEWBIE_TIPS=1` Lua branch is likewise unresolved without the complete cache function: native C++ has no such CVar branch.

Evidence: W `Tooltip_Scripts.cpp:168–181,1717–1734`; `Tooltip.cpp:841–890,895–958,1089–1098,1176–1201,1727–1736,2172–2195`; `Engine/Source/Frame/CSimpleFrame.cpp:1862–1887`; `wowdecomp` search for `UpdateTooltip` found no native match.
