## Q1 — secure group and pet headers

**C cache result for the specified eight-member raid:** children 1–8 receive units `raid1`–`raid8`, in roster/index order. The prerequisites are a nonempty raid roster, a named header, visible header, and names returned for the eight roster entries. `showRaid=true` selects RAID. With neither `groupFilter` nor `nameList`, the header filters by groups 1–8; the default `sortMethod` is INDEX, and default `sortDir` is ASC. No name sort reorders the roster.

With eight displayed units, `unitsPerColumn=4` and `maxColumns=2` produce two columns. For `point=TOP`, the relative point is BOTTOM; child2 is anchored TOP-to-BOTTOM from child1 at `(0,-12)`. A new column anchors from child1: `columnAnchorPoint=LEFT` means LEFT-to-RIGHT with `(20,0)`, so child5 has the requested anchor. Child1 is anchored to the header's TOP and LEFT points. Children are created using the configured `template` (the frame type defaults to Button), assigned their unit attribute, then shown. An unnamed header hides instead of creating children.

**C cache result for the solo pet header:** with no raid/party and `showSolo=true`, group type is SOLO, the sole candidate is index 0 / owner `player`, and `GetPetUnit` maps it to `pet`. With default `useOwnerUnit=false`, an existing pet yields child1.unit=`pet`; no child2 is created. When there is no pet, the candidate is filtered out; `configureChildren` creates at least child1, then hides it and clears its unit, while child2 remains absent. `showSolo` is not enabled by the pet template itself; the instance must set it.

**Update boundary in C:** group headers register `PARTY_MEMBERS_CHANGED` and `UNIT_NAME_UPDATE`; pet headers also register `UNIT_PET`. `OnShow` calls the update routine, and visible headers call it directly from matching events and `OnAttributeChanged`. This is call order in supplied Lua/XML source; not a runtime or native secure-execution guarantee.

## Q2 — AutoHide sequences, handles and attributes

**C cache state model:** each tracked frame is a key in `LOCAL_TrackedHovers`, with a Lua `rectSet` containing the hover state (`"new"`, `false`, `true`, or remaining seconds), TTL, rectangle count, bounding box, main-frame rectangle and child rectangles. Rectangles use `GetRect()` coordinates multiplied by each frame's effective scale. `GetCursorPosition()` is compared directly with those values; the code performs no extra cursor-coordinate conversion. It does not independently establish the API's external coordinate units.

- **A:** shown. The target and child rectangles are disjoint but both tracked. Entering either keeps state `true`; dwell over the child does not count down. The first `OnUpdate` that detects leave from the full rectangle set loads TTL=1 without subtracting that update's elapsed time. If the stated 0.30 seconds is that detection update, TTL remains 1; if a separate detection update precedes it, TTL becomes 0.70. Either sequence remains shown.
- **B:** hides. The first 0.05-second outside update detects leave and starts TTL=1 without consuming 0.05. The next 0.75 leaves 0.25; the next 0.30 takes the counter to -0.05. Expiry is `<=0`; the frame is removed from tracking, hidden, and `statehidden=true` is set.
- **C:** remains shown. The 0.05 leave-detection update starts TTL=1; the next 0.25 leaves 0.75. `UnregisterAutoHide` removes the frame from the tracking table but does not hide it or set `statehidden`. The subsequent 1.25 seconds outside cannot hide an untracked frame.

The child must be added immediately after registration and before the first `OnUpdate`; `AddToAutoHide` errors if the parent is absent or no longer in `"new"` state. A re-registration resets an existing rect set to `"new"`. If the main frame moved since registration when the cursor leaves, the driver discards tracking rather than applying the TTL.

**Secure/handle routing in C:** `RegisterAutoHide` and `UnregisterAutoHide` call private operations directly when `issecure()`; otherwise they pass frame/TTL through attributes on `LOCAL_UpdateFrame`, whose `OnAttributeChanged` handler performs the operation. `AddToAutoHide` has the same direct/insecure split; its insecure branch checks the registered/new state before setting manager attributes. The manager is created from `SecureFrameTemplate`, but the same file comments that it may need to be made secure; the handler is not shown as a restricted snippet. `RestrictedFrames.lua` exposes handle methods that unwrap the owner frame. `HANDLE:AddToAutoHide` specifically requires a userdata handle that resolves through the protected-frame table; global `AddToAutoHide(frame, child)` uses frame objects. `issecure()` and those Lua branches do not prove actual engine combat/taint permission. W's generic `SetAttribute` gate is described above; it cannot establish this C API's protected-frame runtime behavior.

Evidence C: `SecureHoverDriver.lua:5–75,99–179,186–298`; `RestrictedFrames.lua:27–67,616–637`; `SecureHandlers.lua:38–66`. Evidence W for generic attributes: `CSimpleFrame_Scripts.cpp:782–829`; `CSimpleFrame.cpp:541–569,583–591,2160–2176`. These are cache-source sequences, not original-MPQ or runtime test results.

## Q3 — secure click phase, hardware context and actions

**C cache wiring:** `SecureFrameTemplate` is marked protected; `SecureActionButtonTemplate` wires `SecureActionButton_OnClick`, and `SecureUnitButtonTemplate` wires `SecureUnitButton_OnClick`. `SecureUnitButton_OnLoad` assigns `*type1="target"`, `*type2="menu"`, and `unit`. Button suffixes map LeftButton→1 and RightButton→2. The unit-button click wrapper accepts `(self, button)` only; it calls `SecureActionButton_OnClick(self, button)` without forwarding `down`. The general action handler accepts `(self, button, down)` and uses `downbutton` only when `down` is truthy. Thus the cache's secure unit-button wrapper ignores down/up as an action remapping input; a direct SecureActionButton invocation can remap the button on `down=true`.

The native `CSimpleButton` default click mask is LeftButtonUp. `RegisterForClicks(...)` maps explicit phase names such as LeftButtonDown/Up, AnyDown and AnyUp to mask bits. The supplied SecureTemplates XML does not itself register another phase; callers may alter the button mask elsewhere. Physical mouse-down dispatches `OnClick(button,1)` when enabled by the mask. Mouse-up on a pushed button dispatches `OnClick(button,0)` when the release mask and hit rectangle match; an eligible repeated click may instead invoke `OnDoubleClick`. OnClick script execution is PreClick→OnClick→PostClick. These are native reconstructed input semantics, not proof of 30300/12340 runtime hardware provenance.

**C action handlers:**

| Configuration | Cache handler effect |
|---|---|
| `*type1="target"`, unit party1/player | LeftButton suffix selects type1; resolves modified unit, then calls `TargetUnit(unit)` unless spell targeting or cursor-item paths take precedence. |
| `*type1="focus"`, unit party2 | Calls `FocusUnit(unit)`. |
| `*type1="assist"`, unit party1 | Calls `AssistUnit(unit)`; its target is the party member's target. |
| `type="macro"`, macrotext | Calls `RunMacroText(text, button)`; with a macro index it calls `RunMacro`. |
| `type="spell"`, spell 19750 | Numeric spell value calls `CastSpellByID(19750, unit)`; strings use `CastSpellByName`. |
| `type="action"`, ActionButton1 | Computes the action slot with `ActionButton_CalculateAction`, then calls `UseAction(action, unit, button)`. |

The general handler resolves modified unit, remaps to `harmbutton`/`helpbutton` according to attack/assist disposition, rejects a nonexistent unit, resolves the modified action type, then invokes its built-in/custom handler. A string `_actionType` handler runs through `SecureHandler_OnClick`. A function from the `_actionType` attribute is marked at-risk and called after `forceinsecure()`; a function retrieved from `rawget(self, actionType)` is treated as carrying its own taint and called without that forced-insecure transition. The `menu` type on SecureUnitButton stops active spell targeting before dispatch. After the selected action, a spell that targets an item may consume target-bag/slot/item attributes.

The cache handler code contains no explicit hardware-event check or `InCombatLockdown` test. It is an OnClick handler attached to a protected template; direct Lua invocation can execute the Lua body, but does not establish trusted secure context. In W, native `Target` and `SetFocusTarget` reject tainted calls; protected native operations have separate gates. So “out of combat” alone does not prove a direct addon-tainted call is authorized. Native target state updates synchronously if allowed (selection send→spell usability→`PLAYER_TARGET_CHANGED`); focus updates then signals `PLAYER_FOCUS_CHANGED`; assist can call the target path and optionally enter combat. The Lua cache invokes macro/spell/action APIs sequentially, but actual cast completion and a universal result-event order are not established. There is no retry loop: calling twice may duplicate the action. `down=true` can select a `downbutton` only on the general action handler; SecureUnitButton discards it.

## Q4 — combo points, target frames and older counterparts

**C cache: player/combo chain.** `PlayerFrame_OnLoad` registers `PLAYER_ENTERING_WORLD`. Its handler calls `PlayerFrame_ToPlayerArt`, which resets player/pet units, updates the pet and player frames, calls `BuffFrame_Update`, then `ComboFrame_Update`. `ComboFrame_Update` reads `GetComboPoints(PlayerFrame.unit, "target")`. A positive value shows/fades in ComboFrame, displays point widgets and highlights points above `COMBO_FRAME_LAST_NUM_POINTS`, then stores the new count. Zero clears the first point's highlight/shine, hides ComboFrame and stores zero. Its own event handler calls the same update on `PLAYER_TARGET_CHANGED` and matching-player `UNIT_COMBO_POINTS`. Thus the cache source updates `COMBO_FRAME_LAST_NUM_POINTS` to 3 and then 0 in the respective calls; visual fade animations are separate. W's combo server-message handler stores target/count, updates spell usability and directly dispatches the unit signal, so the reconstructed event path is synchronous at the code-call boundary. Neither source is a measurement of original client runtime timing.

**C cache: target visibility/events.** `TargetFrame_Update` hides when `UnitExists(self.unit)` is false; otherwise it shows and updates unit data/auras. It has no special visibility branch for targeting self, party1–4 or an enemy: each exists target is shown; clearing target hides. On `PLAYER_TARGET_CHANGED`, the handler first calls `UnitFrame_OnEvent`, then updates the frame, updates raid icon, closes dropdowns, and plays an enemy/friend/neutral sound if the target exists. Hiding the frame also runs `TargetFrame_OnHide` (lost-target sound and dropdown close) during the update path. In W, a valid native target change updates local selection, sends `CMSG_SET_SELECTION`, updates spell usability and signals `PLAYER_TARGET_CHANGED`; target clear has its separate zero-selection path. These establish order within the respective source handlers, not ordering among all event listeners or runtime timing.

**F1–F6:** C `Bindings.xml` defines command handlers including `TARGETSELF` and `TARGETPARTYMEMBER1`–`4`, but supplies no physical F1–F6 assignments. The TOC order does not provide a key map; the actual default F-key commands remain unresolved from supplied files.

**Portrait/aura counterparts:** C `TargetFrame.xml` has a 64×64 `$parentPortrait` texture, not `TargetFrameContainer.Portrait`; the supplied files contain no `CircleMask` or `ReplaceOtherPlayerPortraits`. Target buffs/debuffs are separate templates with icon, `$parentCount` FontString, cooldown, and for buffs a stealable overlay—not a forbidden/public Count split. Native W counterparts are `SetPortraitTexture`/`RenderPortraitTexture` with the older portrait mask path and `CGUnit_C::GetAuraCount()`/aura data access; these do not implement the newer template/container semantics.

## Q5 — UnitFrame tooltip, UpdateTooltip and fade

**C cache enter/leave path:** `GameTooltip_SetDefaultAnchor` calls `tooltip:SetOwner(parent, "ANCHOR_NONE")` and positions it. `UnitFrame_OnEnter(self)` normally calls `UnitFrame_UpdateTooltip(self)`, which sets that owner, calls `GameTooltip:SetUnit(self.unit, self.hideStatusOnTooltip)`, and assigns `self.UpdateTooltip=UnitFrame_UpdateTooltip` only when SetUnit returns truthy (otherwise it clears that field). `UnitFrame_OnLeave()` has no `self` parameter: with `SHOW_NEWBIE_TIPS="1"` it calls `GameTooltip:Hide()`; otherwise it calls `GameTooltip:FadeOut()`. It does not clear the frame's `UpdateTooltip` field.

For the stated **ordinary frame** (not the global PlayerFrame or qualifying TargetFrame), `SHOW_NEWBIE_TIPS="1"` on enter does not take either special newbie-tip branch; it falls through to `UnitFrame_UpdateTooltip`. The global flag still makes its leave branch call Hide. For the actual PlayerFrame, newbie mode adds the party-options newbie tip and returns before `UnitFrame_UpdateTooltip`; a qualifying controlled TargetFrame likewise adds a newbie tip and returns. Those special entries therefore do not set `UpdateTooltip` on that entry, though they do not clear a pre-existing field.

`GameTooltip_OnUpdate` periodically calls `owner:UpdateTooltip()` when an owner has that field. This creates the reported conflict: when SetUnit returned truthy, a normal leave starts a native 2s FadeOut but the tooltip's next due OnUpdate can call `UnitFrame_UpdateTooltip` again. That calls SetOwner (which resets fading/alpha even for same-owner calls), then SetUnit/Show, so it can cancel the fade. The numeric `TOOLTIP_UPDATE_TIME` value is not included in the 13-file cache, so exact callback-vs-2s timing cannot be concluded. If SetUnit returned false (no UpdateTooltip callback), normal FadeOut completes after 2s. The periodic callback's field remains set unless Lua explicitly clears it; neither UnitFrame_OnLeave nor native C++ does so. A hidden tooltip's native owner becomes nil, so GameTooltip_OnUpdate no longer calls that owner's callback.

**Separate simulator-fixture disposition:** agent-server's F15 handoff records approval for a Wrath-only exclusion of `unit_frame_onleave_fades_out_game_tooltip`. I verified commit `6564cacf00cf28cc788a26f88aebdf6b8ac20045` in `/home/osso/.worktrees/wow-ui-sim-wrath-fixture-f15`; it is an ancestor of HEAD `f922e97629e5cefc1abdfff9f8b0804f9981163e`. Its diff only wraps the unchanged test in existing `post_wrath_ui_fixture!`; the handoff receipt records identical before/after test-body hashes. The handoff plan leaves runtime acceptance unchecked; no test/build was run. Approval provenance here is the handoff plan (`PLAN.md:12`), not an independently retrieved user message. This test disposition is not evidence of shipped-12340 FrameXML or runtime behavior.

**Reconstructed native C++ behavior:** for `ANCHOR_NONE`/other non-cursor anchors, FadeOut starts at 2.0 seconds; cursor/cursor-right anchors hide immediately. When elapsed reaches zero, native tooltip update restores alpha and calls Hide. Tooltip HideThis calls SetOwner(nil) and then base hide, clearing native owner/content. `GetOwner()` returns the owner frame or nil. Native SetUnit builds/shows a valid unit tooltip even when its numeric return is zero; it returns nonzero when the threat row is added. The `frame.UpdateTooltip` Lua property is not a native field, and no native FadeOut/Hide/owner path found here clears it. `OnTooltipCleared` is a Lua callback hook, but it does not itself imply that arbitrary frame fields are cleared.
